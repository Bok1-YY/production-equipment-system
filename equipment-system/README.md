## 三级成员与报修流程

系统里的每个人都有一个级别，级别决定能看到什么、能做什么。级别由管理员在“成员管理”里指定。

| 级别 | 角色 | 能做什么 |
|---|---|---|
| 一级 | 普工 | 扫码报修（一句话即可，故障分类不用选）；**撤回**误报；查看**自己报修的**工单进度；工单完成后**给技术员打分**；没修好可以**重新报修**。看不到别人的工单，也看不到台账和产线组合。 |
| 二级 | 技术员 | 在待接单池抢单，走完接单→到场核对报修信息→维修→试运行→**结单**；维修阶段填写诊断原因、维修方法、使用零件和必要的完成照片，错误零件可删除重填；进入待试运行后只能填试运行结果，资料有误需显式返回维修。执行管理员派发的技改任务，确认方案、到场、施工、逐项填写结果和现场拍照；只能看到分配给自己的任务。**只能推进自己接的单。**巡检。设备台账和产线组合只读。只能看到**自己的综合评分**，看不到单条评价。 |
| 三级 | 管理员 | 指派或中途转派工单、在任何未结阶段取消工单、设备台账、产线组合、发布和审核技改任务、点检保养计划、故障代码、服务评价、运营报表、成员管理和审计日志。 |

报修流程：

```
普工报修 ──▶ 待接单池 ──▶ ①已接单 ──▶ ②已到场 ──▶ ③维修中 ──▶ ④待试运行 ──▶ ⑤已完成
    │           技术员点   「我到现场了」  核对设备与分类  「转试运行」    「结单」
    │           「我接这单」       │        填诊断原因/方法      │              │
    └── 撤回（到场前，填原因）     └─「开始维修」─ 等零件/外协   只显示三选一     普工评价（可带照片）
                                                   ▲              │              │
                                                   └── 资料有误返回维修      没修好？重新报修
```

技术员每一步只需要点**一个写着动作名字的按钮**（"我到现场了""开始维修""结单"），工单详情顶部有一条**步骤条**显示当前走到第几步、还剩几步。到场阶段只有一块「核对报修信息」：故障分类和“报修信息有误，更改设备？”放在一起；一旦开始维修，这块默认不再出现。确实发现核对错了时，使用单独的返回按钮回到上一步修改，服务端也会阻止跨阶段直接篡改。

**结单由技术员自己完成，不需要管理员在场**——验收由报修人的评价承担。

几条规矩：

- **谁接的单谁推进**。别的技术员想接手，得让管理员转派（转派会在工单历史里留痕）。这样"这次是谁修的"和报修人的评价归属才不会串。
- **接单和到场是两回事**。接单只表示有人负责了，到场才开始算维修时间。
- **取消工单只有管理员能做**，但任何还没结束的阶段都能取消——误接的单不会永远挂在列表里。普工要撤销自己的误报走「撤回」。

## 设备改造／产线变动任务

管理员在「技改任务」中先保存草稿，编排一张任务内的多个设备或结构项目，指定主负责人和协作技工，并上传 PDF、Office、图片、DWG/DXF 或 ZIP 技术资料。设备项目支持安装、移动、拆除、替换和档案改造；结构项目支持新增、改名/排序、调整所属、启停和安全删除。旧版设备变动只保留历史查询，不能再从旧入口新建或审批。

```text
管理员草稿与上传图纸 → 发布方案 → 所有技工确认本版
                                  ↓
主负责人确认到场 → 开始施工 → 逐项结果与完工照片 → 提交审核
                                  ↓
                  管理员退回整改 / 审核通过整单生效
```

- 任一执行人未确认当前版本时不能开工；管理员修订方案会使旧确认失效，但未改项目的施工证据仍保留。
- 技工发现图纸与现场不符可上报偏差，任务进入待修订；管理员发布新版本后所有执行人必须重新确认。
- 影响生产的任务执行期间，涉及设备显示「改造中」，对应产线显示「调整中」；维修状态优先于改造状态。
- 每个要求拍照的项目必须同时填写实际执行结果并上传至少一张完工照片，才能提交审核。
- 管理员审核时重新校验现场状态，并在一个数据库事务中应用全部项目；任何项目冲突都会整单回滚，不会留下半台设备已移动、另一项失败的中间状态。
- 结构删除仍遵守历史保护：只有完全无设备、无安装历史、无工单和其他业务记录的空结构才允许删除。

## 普工报修：扫码 + 一句话

普工报修只需要两件事：**扫设备上的二维码**（工序和设备自动填好），**说一句哪里不对劲**。

```
扫码 → 「3号挤出机不出料了」 → 提交
```

### 手动选设备：车间 → 产线 → 设备

扫不到码（码磨掉了、手机没带）就手动选。**不是一个 205 项的长列表**，而是一级一级缩：

```
[🔍 搜设备编号、现场名称或类型]     ← 打字直接筛，跨车间跨产线
[开槽车间 ▾]  [1#开槽产线 ▾]      ← 选了就只剩这条线上的
[03 · 1#开槽分切多片锯 · YSM-SAW-MULTI-0001 ▾]
```

设备选项上带着**工位顺序**和**现场叫法**——车间里管它叫"1#开槽分切多片锯"，站在线上一眼就对得上，不用去认 `YSM-SAW-MULTI-0001` 这种编号。同一条线上的设备按工位从头到尾排，跟你走过去的顺序一致。

不想一级一级点就直接在搜索框里敲，编号、现场名称、设备类型、机位编号都能搜。

这套选择器在**报修、巡检、技改任务**三个地方是同一个，学会一处就都会用了。

故障分类**不用普工选**。让一线工人为了报一句"机器不转了"在三级分类里翻，是原先这套系统最不合理的一处。分类改由**到场看过的技术员**在「核对报修信息」阶段确认；实际故障设备也在同一处核对。两项未确认时不能开始维修。

界面上仍然给几个**常见故障快捷按钮**，愿意点的点一下就等于选完三级，连那句话都不用打。系统会自己挑该显示哪几个：攒够工单之后按"这类设备最常报的故障"排，刚上线没数据时按管理员标记的常用项排。要求拍照的故障码，按钮上会先标出「需拍照」，不会让人点完才被拦。

还有一件顺带简化的：**工序不用选了**。设备登记了安装位置，系统就知道它在哪道工序上。只有设备还没登记位置、或者普工确实说不清是哪台设备时，才需要选工序。

报修照片仍是按故障类型决定是否强制；设备巡检照片则始终强制现场拍摄，详见「巡检」。

### 报修放得松，结单收得紧

这是整套流程的核心取舍：**普工那一头尽量少填，缺的东西由到场看过的技术员在结单前补齐。**

报修时可以不选设备（"无法判断具体设备"——普工站在产线边上不一定分得清是哪台机器），也可以不选故障分类。但技术员**结单前必须补齐五样**，否则系统拒绝结单：

| 结单必备 | 为什么不能省 |
|---|---|
| 试运行结果 | 必须在“正常运行 / 可运行但仍存在问题 / 无法运行”中选择；第二项必须说明遗留问题，第三项不能结单 |
| 实际维修的设备 | 工单不挂设备，这次维修就记不到任何设备账上，设备履历和 MTBF 全都漏掉它 |
| 故障代码 | 没有代码，故障统计等于没做——"哪类故障最多"就永远算不出来 |
| 诊断原因 | 原“诊断”和“根本原因”已合并，说明最终判断出的故障原因，不能只有一句“已修好” |
| 维修方法 | 记录实际采取的维修动作，便于复盘和重复故障判断 |

缺哪样，「结单前检查」中的缺项行本身就是按钮：试运行缺项会定位到试运行选项；诊断、维修方法或完成照片缺项会先把工单退回维修中，再自动滚动并聚焦对应表单；设备或故障分类缺项会返回核对阶段。

到了「待试运行」阶段，维修记录、使用零件和完成照片编辑区不再重复出现，只保留结构化试运行结果和**结单前检查**。确实发现维修资料填错，可点「维修资料有误？返回维修」；错误零件在维修阶段删除后重新填写。未补齐时结单按钮会明确提示还差几项。

误报产生的无主工单不受这三条限制——撤回和管理员取消照常可用，否则那些单子会永远挂着。

### 四段时长

工单会记下四个时刻：**报修 → 接单 → 到场 → 完成**。所以"路上花了多久""到场后修了多久"可以分开统计，工单详情里直接显示，总览页给出近 30 天的平均响应时长和平均维修时长。转派不会覆盖首次接单的时刻——"报修到有人接"按第一个接手的人算。

## 启动

Windows 统一使用桌面的 `一键启动全功能设备系统.bat`。它固定连接 `factory-data/equipment.db`（当前 205 台设备的工厂运行库），缺失时拒绝静默创建空库。它会自动检测当前 Wi-Fi 地址；APK 缺失、移动端源码更新或 Wi-Fi 地址变化时，会先自动准备便携 JDK/Android SDK 并重新打包，确认安装包可下载后再启动同一套完整后端。首次构建需要确认 Android SDK 许可并下载依赖，可能耗时数分钟，以后会复用缓存。启动器等待 `/api/health` 成功后打开电脑页面，窗口中同时显示手机访问、安装地址和实际数据库路径，并停留到手动关闭。关闭启动窗口不影响服务，需要停止时双击项目内的 `stop-windows.bat`。启动日志位于 `data/server-*.log`。电脑和手机使用同一套功能、账号和数据，不再区分“电脑版/手机版/测试服务”。

Linux 可以在项目目录双击 `一键启动设备系统.sh`。

手动启动方式：

```bash
cd production-equipment-system/equipment-system
npm ci
npm start
```

浏览器访问：<http://127.0.0.1:8787>

开发模式：

```bash
npm run dev
```

手动执行 `npm start` 时默认数据库仍为 `data/equipment.db`；Windows 日常一键启动会显式设置 `YSM_DB_PATH=factory-data/equipment.db`。用户已确认 `demo-data/equipment-demo.db` 是工厂 205 台设备的源库，不是普通演示数据；为避免 Git 拉取覆盖现场写入，服务使用停服备份后生成的非 Git 运行副本，不直接写源文件。恢复或更换正式数据库前必须停止服务、生成并验证一致性备份，再由用户明确确认。可使用环境变量改变配置：

```bash
HOST=0.0.0.0 PORT=8787 \
PUBLIC_BASE_URL=https://设备系统公司域名 \
YSM_DB_PATH=/安全数据目录/equipment.db \
npm start
```

正式 Docker 部署使用 [compose.production.yaml](compose.production.yaml) 和 [deploy/Caddyfile](deploy/Caddyfile)，参数从 `.env.production` 注入。服务器直接从 GitHub 源码构建时再叠加 [compose.build.yaml](compose.build.yaml)。生产容器固定设置 `YSM_REQUIRE_EXISTING_DB=1`：宿主机数据目录挂错或缺少 `equipment.db` 时拒绝启动，绝不静默创建空库。`DATA_DIR` 与 `BACKUP_DIR` 可适配服务器现有目录；数据库、附件和正式环境变量都不进入镜像或 Git。具体升级顺序见仓库根目录 [Docker服务器升级说明.md](../Docker服务器升级说明.md)。

`PUBLIC_BASE_URL`决定铭牌二维码中保存的地址。**在这个变量配好之前不要批量打印铭牌**——见下面「设备铭牌」一节。

## 设备铭牌

二维码分为两类：设备铭牌一台一个码；工序二维码贴在产线入口或巡查点，扫码后可查看并筛选该工序设备。

在「设备台账」页点**批量打印铭牌**，选车间和产线，就出这条产线的一叠铭牌，**按工位顺序排好**——拿着一叠走一条线贴完，不会串。台账每一行也有单张「铭牌」按钮。

铭牌上印的是：设备编码、现场叫法、标准名称、品牌型号、二维码。

**刻意不印车间、产线和工位。** 设备会调线、会移机、会替换，位置一旦印死在铭牌上，设备一动铭牌就成了错的，反而会让人按过期信息找错机器。位置扫码就看得到，而且取的是系统里的当前值——这套系统本来就记得住每台设备搬过哪些位置、什么时候搬的。

> ⚠️ **批量打印之前必须先定访问地址。**
> 二维码里存的是"打开系统并扫这个设备"的网址。如果没有配 `PUBLIC_BASE_URL`，码里存的就是 `http://127.0.0.1:8787`——这是"本机"的意思，**手机扫了打不开**，205 张铭牌全部作废。
> 打印界面会把实际会存进码里的那串地址显示出来，没配好时挂红色警告。**先定内网 IP 或公司域名，配好再印。** 现在可以先打开看排版。

## 登录与账号

系统首次启动时会自动创建一个管理员账号：

| 工号 | 初始密码 |
|---|---|
| `admin` | `ysm-admin-2026` |

**这个初始密码只能用一次。**首次登录后系统会强制要求修改密码，改密之前除了改密接口以外什么都调不通。改完密码之后，请立刻在“成员管理”里给实际使用的人开账号，并把 `admin` 留作备用或改成真实负责人。

关于账号的几条规则：

- 管理员开户时系统自动生成初始密码，**只在创建成功那一次显示**，之后系统里查不到明文；对方首次登录同样会被强制改密。
- 忘记密码走“重置密码”，同样生成一次性新密码，并立刻踢掉该账号已有的登录会话。
- 账号只能停用，不能删除，避免审计日志断链。
- 系统始终保留至少一个启用的管理员账号，最后一个管理员不能被停用或降级。
- 修改某人的级别或停用某人后，他已经登录的会话立即失效，不需要等他自己退出。
- 登录状态保存在 HttpOnly Cookie 里，最长 12 小时；活动续期不会突破绝对到期时间。Android 后台通知使用独立、可撤销、加密落盘的设备令牌，不保存会话 Cookie。

密码用Node内置的scrypt加盐哈希存储，系统任何接口都不会回传密码哈希或盐值。审计日志里的“操作人”从此是真实登录账号，不再是可以随手填写的文本。

反向代理配置了HTTPS之后，请给服务加上环境变量 `YSM_SECURE_COOKIE=1`，让会话Cookie只走加密连接。

## 首次使用顺序

1. 用 `admin` / `ysm-admin-2026` 登录并按提示修改密码，然后在“成员管理”里至少再建立两名真实管理员（设备科／生产负责人）、技术员和普工账号，技改任务建议由不同管理员分别发布和审核；
2. 在“设备台账—管理类型”核对设备类型代码；
3. 上传整理好的设备台账工作簿（本项目内部使用 `资料整理/2026年最新设备台账_设备命名建议.xlsx`，该目录不入公开仓库；外部使用者用「导入模板」里的台账模板填写即可），系统先预览；只要仍有一行“待核实”或其他错误，整批都不会写入；
4. 全部核实后确认整批导入，由系统按类型和关键规格分配永久码；
5. 在“产线组合”下载组合模板，把旧表整理成一行一个机位，预览无误后整批导入；
6. 也可以在树上逐级创建车间、产线、工序和机位；误建的空分支可在删除安全检查后整枝删除；
7. 正式运行后的安装、移动、拆除和替换在「技改任务」里发布、施工留证并由管理员审核生效；
8. 核对产线树并打印测试铭牌，铭牌二维码可直接扫码报修。

项目根目录的`导入模板`文件夹内固定提供：

- `01_设备台账导入模板.xlsx`；
- `02_产线组合初始化模板.xlsx`；
- `模板填写说明.md`。

页面上的模板下载接口会实时生成同样格式的XLSX文件。设备台账和组合导入都会先预览、后确认，并按整批事务提交，任意一行失败都会全部回滚。组合导入按“永久设备编码 → 原资产编号 → 品牌＋出厂编号”严格匹配，不使用设备名称模糊匹配；无法匹配时，必须提供设备名称、类别、类型代码，系统再按类型和关键规格生成永久设备码。

设备码示例：`YSM-EXT-135-0001`、`YSM-MIX-H800-C2500-0001`、`YSM-PUL-0001`。同一“类型代码＋关键规格”使用独立四位流水，设备码、类型和关键规格在建档后锁定；名称、现场别名等档案字段仍可修改。

产线树只允许删除完全没有业务历史的空分支。存在安装历史、组合变动、维修工单或巡检记录时都会阻止删除，历史工单、零件、评价和附件绝不会因为删结构而被级联清除；正常停用请改用结构状态。

## 点检、保养与运营报表

- 管理员在“结构化点检”或“设备保养”建立模板，每项可设置检查类型、标准、数值上下限和异常拍照要求。
- 计划支持每天、每周、间隔天数、固定一次和手工下发；到期任务自动生成且不会重复。
- 技术员逐项填写结果。数值越界由服务端自动判异常；异常可现场说明关闭，也可直接转为维修工单。
- 保养模板必须指定一级、二级或三级，计划对象可选设备或工序。
- “运营报表”按日期统计响应、维修、停机、重复报修，并提供可下钻的产线故障、故障类别和设备故障排行；设备排行按故障发生时的产线展示，全部结果可导出 Excel。

## 工单评价

工单完成后，**报修的那个人**给这次维修打分。三项，每项五星：

| 维度 | 看什么 |
|---|---|
| 维修质量 | 修得好不好、有没有真正解决 |
| 服务态度 | 沟通、配合、现场行为 |
| 响应速度 | 报了多久才有人来、修了多久 |

外加选填的文字和照片；不会描述时可以直接拍下现场问题。一张工单只能评一次，但**可以随时修改**（改动会留痕）。评价是选填的——不评价工单照样是已完成状态，不会卡住任何人；界面上会挂一个「待评价」角标提醒。

**谁能看到什么，这是刻意设计的**：

| | 单条评价（含评论、照片、评价人） | 技术员综合平均分 |
|---|---|---|
| 普工 | 只看自己提交的 | 看不到 |
| **技术员** | **完全看不到** | **只看自己的** |
| 管理员 | 全部 | 全部（含排行） |

技术员看不到单条评价、评价照片，也看不到是谁评的，是为了**让普工敢如实打分**——能被认出来的话，低分就没人敢给了。但技术员能在总览页看到自己的综合平均分和三个维度得分，知道自己哪方面需要改进。管理员在「服务评价」页能看到技术员排行和全部评价内容。

技术员离职停用之后，他的历史评价仍然计入统计，不会凭空消失。

## 撤回与重新报修

两个防错的口子：

- **撤回**：报错设备了、自己重启一下好了、误操作……在**技术员到场之前**都可以撤回自己的报修，必须填一句原因。技术员已经到现场了就不能再撤——人都来了，撤回等于白跑一趟，这种情况直接跟技术员说。撤回和管理员取消在工单历史里是两种不同的事件，事后分得清。
- **重新报修**：已完成的工单如果问题又出现了，点「重新报修」直接开新单，设备和故障代码自动沿用上一单，不用重填。新单会标明「重报自 WO-xxx」并与原单关联——**几天内就重新报修，本身就是"上次没修好"的信号**。

## 故障代码

按需求说明书采用**三级结构**：

```
故障类别 → 故障部位 → 故障现象
电气故障 → 主电机  → 无法启动 / 异响 / 发热 / 电流过高
机械故障 → 轴承    → 异响 / 卡死不转 / 发热
液压气动 → 管路    → 漏油 / 漏料
综合    → 整机    → 整机无法启动 / 无法正常工作 / 其他
```

**每张工单结单前都必须有故障代码**，所以"哪类故障最多、哪台设备最爱坏"这类统计一条都不会漏。放宽的只是**谁来填、什么时候填**，不是要不要填。

技术员补上分类之后，工单上的故障现象会从普工原话（"3号挤出机不出料了"）变成规范文本（"机械故障 / 轴承 / 异响"），**普工原来那句话仍然留在补充说明里**，不会丢。

> ⚠️ **系统预置的 23 条故障代码是参考旧系统整理的建议值，不是现场确认过的标准。**
> 界面上带「待确认」标记。**请设备科尽快核对**：技术员结单时只能从这个列表里选，列表不准会直接影响故障统计。管理员在「故障代码」页可以随意增删改，改过的会自动去掉「待确认」标记。已经被工单用过的代码只能停用不能删除，否则历史工单的故障归类就断了。

每条故障代码可以配置：

- **处理建议** —— 报修人选中时显示，技术员到场前能先做点什么；
- **默认紧急程度 / 默认勾选停机** —— 比如"短路跳闸"自动带出特急+停机，报修人仍可改；
- **必须拍照** —— 漏油、外观损坏这类看照片就能判断的强制拍照，"异响"这种拍了也没用的不强制。（注意：普工不选故障码时这条要求无从生效，因为那时还不知道是什么故障。）
- **放进常见故障快捷按钮** —— 只勾普工站在机器边上就判断得了的，比如"整机无法启动""漏油"。攒够历史工单之后，快捷按钮会自动改按报修频次排，这个勾选就只在头几周起作用。

**照片**：报修、评价和工单处理过程可拍照或上传；巡检必须通过实时摄像头至少拍一张，不接受相册旧图，并自动写入设备、巡检人和时间水印。巡检转出的维修工单修完后还必须通过实时相机拍摄“维修完成照片”，自动写入设备、维修人和时间水印；普通补拍照片不能代替，缺少时服务端拒绝结单。图片按长边 1600 像素压缩，每条记录最多 6 张、单张不超过 2MB。照片可见性跟随所属业务，评价照片只对评价人和管理员开放。

## 巡检

技术员每天到现场转一圈，看到问题就记一笔。刻意做得很轻：**扫码选设备 → 拍照 → 写清楚发现了什么、怎么处理的**，没有逐项打勾的巡检表。

- 「设备巡检」页在技术员和管理员那里可见，普工看不到；
- 扫设备铭牌二维码时，技术员会看到「登记巡检 / 报修」二选一（普工直接进报修）；
- 提交前必须通过摄像头现场拍摄至少一张带设备、巡检人和时间水印的照片；更换设备后必须重新拍摄；
- 有几个快捷按钮（运行正常 / 已润滑保养 / 已紧固）避免为了必填而乱写；
- 当场解决不了的，点「转维修工单」直接开单，巡检发现会自动写进工单说明，不用重打一遍，两边互相关联；
- 技工开始维修后会看到独立的「维修完成照片（结单前必拍）」区域；只有接单技工或管理员能现场拍摄，至少一张才能结单；
- 巡检记录会进设备档案的「巡检记录」标签页。

## 设备状态与设备档案

设备状态共六个值，**前四个由管理员手工维护，后两个由维修工单自动维护**，界面上不给手工选：

| 状态 | 谁来维护 | 什么时候出现 |
|---|---|---|
| 在用 / 闲置 / 停用 / 报废 | 管理员在设备档案里选 | 随时 |
| 已报修 | 系统自动 | 普工提交报修，还没有技术员开工 |
| 维修中 | 系统自动 | 技术员进入“维修中”之后，直到结单或取消 |

台账列表和产线组合树都会实时显示这个状态，产线树上处于维修状态的机位整行标黄，不展开也能看见哪台在修。

状态是**从未结工单推算出来的**，不是报修时设一下、结单时改回去。所以一台设备同时挂着两张工单时，关掉其中一张不会提前恢复，要全部结束才恢复。

维修期间管理员仍然可以改状态，改的是“结单后要回到的状态”：比如设备在修的时候你把它改成“闲置”，台账仍显示“维修中”并注明“结单后回到闲置”，工单一结束就自动落到闲置，不会被冲回“在用”。

点台账任意一行的「档案」，或产线树上设备节点的「档案」，打开设备档案抽屉，四个标签页：

- **基本信息**：管理员可编辑，技术员只读；
- **位置变动**：这台设备什么时候装在哪个机位、什么时候搬走、哪张变动单、谁提交谁审核；
- **维修记录**：每次报修的故障现象、诊断原因、维修方法、结构化试运行结果、停机时长和更换的零件。报修时挂错设备、后来被修正走的工单也会列出来并标注“报到这台，实际不是这台”，但不计入维修次数；
- **档案修改**：谁在什么时候改了哪个字段、从什么改成什么，含状态联动记录。

顶部固定显示统计：维修次数、未结工单、累计停机分钟、更换零件数、位置变动次数、上次维修时间。技术员也能看完整履历——查维修史是他们的刚需；普工进不了台账页，不开放。

身份完全来自登录会话，页面上没有任何可以自选的角色。所有业务接口在没有有效会话时一律返回401，权限在服务端按级别校验，前端隐藏用不上的入口只是为了界面清爽，不构成安全边界。

后续如果要接入公司用户目录或微信身份绑定，替换`src/auth.js`里的密码校验与会话签发即可，级别到权限的映射不用动。

- 巡检记录、发现必填、普工无权、问题发现和维修完成两阶段现场水印照片、转维修后双向关联并触发设备状态联动；
- 试运行结果只能在待试运行阶段填写；待试运行不重复显示维修记录和零件；“可运行但仍存在问题”必须说明，“无法运行”禁止结单；
- 运营报表的产线、故障类别和设备排行及权限一致的工单下钻；
- 永久设备编码格式和流水；
- 不同类型、不同关键规格的独立流水；
- 设备类型目录新增、改名和使用保护；
- 设备二维码映射；
- 一个设备一个当前机位；
- 一个机位一台当前设备；
- 安装、移动及历史组合查询；
- 技改任务全员确认、版本修订、技术文件、逐项结果与照片、权限隔离、通知深链、管理员退回/通过，以及多项目审批冲突时整单回滚；
- 全厂组合树和Excel组合初始化；
- 导入预览不落库、严格设备匹配及重复文件拦截；
- 设备台账待核实整批阻断及事务回滚；
- 空结构分支递归删除、有历史分支阻断；
- 设备变动角色权限；
- 维修工单状态机；
- 维修详情、零件记录和审核闭环；
- 审计日志。

## 数据备份

正式环境统一执行 `scripts/backup-production.js`：脚本使用 SQLite `VACUUM INTO` 生成一致数据库，同时归档附件并生成 SHA-256 清单。不要在服务运行时直接复制主文件，因为可能还有 `equipment.db-wal`；恢复前必须停 App，并先用 `scripts/verify-backup.js` 校验。正式服务器至少配置每日备份、异机保存和定期恢复演练。

更详细的数据规则见[设备编码与组合规则](docs/设备编码与组合规则.md)。
