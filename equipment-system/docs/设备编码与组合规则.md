# 设备编码与组合规则

## 永久设备码

设备码按设备类型和原台账明确存在的关键规格生成：

```text
YSM-{类型代码}-{关键规格}-{四位流水号}
YSM-{类型代码}-{四位流水号}            # 没有明确关键规格
```

示例：`YSM-EXT-135-0001`、`YSM-MIX-H800-C2500-0001`、`YSM-PUL-0001`。其中混料机原参数`800/2500`写成`H800-C2500`，明确表示热混容量800、冷混容量2500，避免被误读为数值范围。

设备码表示设备本体及建档时确认的分类属性，不包含车间、产线、工序、机位、品牌或负责人。

- 创建成功后不得修改；
- 类型代码和关键规格在建档后锁定；
- 调线、移机、改名时保持不变；
- 停用或报废后不得重用；
- 错误号码应作废，不能重新分配；
- 普通零件不分配设备码。

类型代码使用2至4位大写英文字母；关键规格只允许大写字母、数字和连字符。每一组“类型代码＋关键规格”独立使用`0001`至`9999`流水。系统通过数据库事务集中发码，批量表中的“建议永久设备编码”只用于比对，最终号码以系统预览和提交结果为准。

设备类型目录可在台账页面维护：代码创建后锁定，中文名称可修改；未被设备使用的类型可删除，已经使用的类型不允许删除。

## 二维码与铭牌

**二维码只贴单台机器**，一台一个，打成铭牌。扫码进入该设备并可直接报修。

铭牌上印设备编码、现场别名、标准名称、品牌型号和二维码，**刻意不印车间、产线和工位**——设备调线移机后铭牌不会变成错的，位置扫码取当前值。批量打印按产线出，铭牌按工位顺序排。

工序不是扫码对象：在本厂语义下"工序"是产线下的顺序，`positions.sequence_no`（工位）才是工人认机器的依据。库里早期给工序发过 57 个码，没有打印入口，扫到会按所属产线处理。

> 二维码内容是 `${PUBLIC_BASE_URL}/?scan=<token>`。**该变量配好之前不要批量打印**——否则码里是本机地址，手机扫不开。token 是稳定映射，换地址只需重新打印，但已贴的旧牌会失效。

## 设备选择与工位

手动选设备走**车间 → 产线 → 设备**三级，另有搜索框（编号、现场别名、类型、机位编号）。设备选项显示`工位顺序 · 现场别名 · 设备编码`，同一条产线按工位从头到尾排——工人认的是"这条线第几位的那台"，现场别名才是车间里真正的叫法。报修、巡检、设备变动三处用同一套选择器。


## 独立设备判定

满足任意一项即可独立建档：独立启停、独立报修、独立点检保养、有独立铭牌或出厂号、可独立调拨更换、会独立导致停机、需要单独核算维修历史。

## 位置与组合

```text
生产车间
└── 产线 YSM-L01
    └── 工序 YSM-L01-EX
        └── 机位 YSM-L01-EX-P01
            └── 当前安装设备 YSM-EXT-135-0001
```

组合不是设备档案中的固定字段，而是有起止时间的安装关系。系统因此能够回答：

- 一条产线目前由哪些设备组成；
- 某个历史日期由哪些设备组成；
- 某台设备曾经安装在哪里；
- 谁提出变动、谁确认、何时生效以及为什么变动。

## 设备变动

首期支持安装、移动、拆除、替换。三级角色模型下由一名管理员提交，另一名管理员复核后才正式更新安装关系；系统禁止提交人自审。

- 一个设备只能有一条未结束的安装记录；
- 一个机位只能有一台当前设备；
- 生效时间不能早于设备当前安装时间；
- 审核时重新检查目标机位和设备状态；
- 已发生的错误记录不能覆盖，应以撤销或新的纠正记录处理。

## 维修工单与成员级别

维修工单模块已启用，按三级成员运行：普工（一级）报修，技术员（二级）抢单并完成维修**并自己结单**，报修人在工单完成后给这次维修打分。

工单走五个阶段：**待接单 → 已接单 → 已到场 → 维修中 → 待试运行 → 已完成**（等零件、外协是维修中的分支）。

> **2026-07-26 变更**：原先「已分派」和「已接单」是两个状态，语义重复，技术员到场前要白多点一下。合并为「已接单」——管理员指派和技术员抢单都落到这一个状态，谁做的靠工单历史区分。接单只能通过"接单/指派"完成，不能通过状态流转，否则会产生"已分派但没有负责人"的工单。

两条推进规则：

- **谁接的单谁推进**。别的技术员要接手，必须由管理员转派（历史里记 `REASSIGNED`）——否则"这次是谁修的"和报修人的评价归属会串。管理员不受此限。转派一张已经在修的单不会把它退回上一阶段。
- **到场之后才能做到场之后的事**。修正故障设备、确认故障分类、填写维修记录、记录使用零件这四件，都要求工单已经推进到「已到场」——没到现场看过，判断不了是哪台设备、什么故障，更不会用掉零件。管理员不受此限（把明显的误报在派单前改掉是合理的）。

**取消工单只有管理员能做，但任何未结阶段都能取消。** 原先到场之后既不能撤回也不能取消，而结单要满足完整性硬校验，一张误接的垃圾单会永远挂在列表里。

> **2026-07-26 变更**：原先是"技术员修到待审核为止、管理员验收结单"。改为技术员直接结单，验收由报修人的评价承担。原因是管理员不在线时工单会卡住，而真正知道"修没修好"的是报修的那个人。`PENDING_REVIEW` 状态保留但不在正向路径上，只为让改造前停在该状态的历史工单还能结单。

**结单有五道硬校验**：试运行结果非空、**故障设备归属非空**、**故障代码非空**、**诊断结论非空**、**维修措施非空**。

报修入口允许"无法判断具体设备"（需求 9.2），也允许不选故障分类，但技术员修完一定知道自己修的是哪台、是什么故障，必须用「修正故障设备」和「确认故障分类」补齐，并留下诊断与维修措施后才能结单——工单不挂设备就结掉，设备状态联动、维修履历和 MTBF 之类的统计全部落空；没有故障代码则故障统计等于没做。`CANCELLED` 和撤回不受此限，否则误报产生的无主工单会永远挂着。

**四段时长**：报修 → 接单 → 到场 → 完成，四个时刻分别记在 `reported_at` / `assigned_at` / `arrived_at` / `completed_at`。转派不覆盖首次接单时刻，"报修到有人接"按第一个接手的人算。总览页给出近 30 天已完成工单的平均响应时长（报修→到场）和平均维修时长（到场→结单），只统计时间戳齐全的工单。

普工撤销自己的误报走**撤回**（`withdrawWorkOrder`），只允许在技术员到场之前（`SUBMITTED`/`ACCEPTED`），必须填原因，历史事件记 `WITHDRAWN` 以区别于管理员取消。

已完成的工单如果问题再次出现，报修人可以**重新报修**：新单继承原单的设备与故障代码，并通过 `work_orders.reopened_from_work_order_id` 关联原单。短期内重新报修是"上次没修好"的直接信号。

## 工单评价

报修人对已完成的工单打分，三个维度各 1~5 星（维修质量、服务态度、响应速度）+ 选填评论。一单一评，可修改。技术员姓名在评价里做快照，离职停用后历史统计仍然成立。

可见性是刻意设计的：**技术员完全看不到单条评价和评价人，只能看到自己的综合平均分**；普工看自己提交的；管理员看全部并有技术员排行。技术员看不到单条，是为了让普工敢如实打分——能被认出来的话低分就没人敢给了。

实现上有两个必须同时做到的点：接口层把 `review` 剥成 `null`（保留 `has_review` 让界面知道"评过了"），**并且工单历史里不能写入评分和评论**——`work_order_history` 对技术员可见，内容写进 `note` 或 `details_json` 就会从时间线漏出去。

工单必须落到具体设备上才有统计价值。报修时允许不选设备，但技术员到场后应使用“修正故障设备”把工单挂到实际维修的那台设备，`final_equipment_id` 才是维修历史的归属依据。

成员只有级别，没有可自选的角色。身份来自登录会话，级别在服务端映射为权限令牌，审计日志的“操作人”即真实登录账号。账号只停用不删除，系统始终保留至少一个启用的管理员。

## 故障代码

按需求说明书第 11 章采用三级结构：**故障类别 → 故障部位 → 故障现象**。

> **2026-07-26 变更**：原先要求普工报修时必选故障码。改为**报修选填、结单前必填**。原因是让一线工人为了报一句"机器不转了"在三级分类里翻，是整个系统最不合理的一处；而到场看过的技术员分类本来就更准。这**不是**打开"只填自由文本"的旁路——旁路的危害是故障统计落空，而这里只是把录入点从报修挪到了结单，统计一条不少。

- 普工不选故障码时**必须写一句话说明**（例如"3号挤出机不出料了"），否则这张工单对技术员没有任何信息量。那句话会回填成故障现象，所以工单列表上显示的是普工原话。
- 技术员用「确认故障分类」补码后，故障现象被重写成三级文本（如"机械故障 / 轴承 / 异响"），**普工原话仍保留在补充说明里不会丢**。
- 报修页有「常见故障」快捷按钮：点一下等于选完三级，普工可以不打一个字就提交。选谁由系统定——有历史工单时按这台设备类型的报修频次排，刚上线没有数据时按管理员标记的"常用"排。要求拍照的故障码，按钮上会先标出「需拍照」。
- 已知代价：故障码上的"必须拍照"要求在"不选码"这条路径上无法生效，因为报修时还不知道是什么故障。
- 选中的故障码会把可读文本回填进 `work_orders.fault_symptom`，所以工单列表、设备履历、审计日志这些下游展示不需要改动；`fault_code_id` 才是用于统计的结构化字段。
- 兜底码 `GEN-ALL-OTHER`（"其他"）选中时强制填补充说明，并用补充说明回填故障现象。它不出现在快捷按钮里——点了还要再填文字，和"不选码直接写一句话"完全重复。
- 每条码可配置：处理建议、默认紧急程度、默认停机、是否必须拍照、适用设备类型（留空=全部设备）。
- 系统预置 23 条**建议值**（`src/fault-codes.js`，按旧系统 YEMS 的 21 个扁平故障码整理），标记 `is_seeded=1`，只在表为空时种入——管理员删掉的预置项不会在重启后复活。**待设备科确认。**
- 已被工单引用的故障码只能停用不能删除，避免历史工单的故障归类断链。

## 现场照片

报修、巡检和工单处理都可以带照片。走与 Excel 导入相同的 base64 通道，不引入 multipart 依赖；前端先压到长边 1600px、JPEG 0.8 再传。

服务端**只认魔数字节**（JPEG/PNG/WEBP），不信前端声明的 mime——否则改个扩展名就能上传任意文件。单张 ≤2MB、每个对象 ≤6 张。文件落在 `data/attachments/YYYYMM/` 下、文件名随机，数据库只存相对路径。照片可见性跟随其所属工单：普工看不到别人工单的照片，也看不到巡检照片。

## 巡检

技术员的日常现场巡查，**不是旧系统那种逐项打勾的巡检表**：扫码选设备 → 拍照 → 必填一段"发现的问题与处理"。刻意做得轻，否则没人愿意每天填。

只给设备不给工序时，系统会按当前安装关系自动带出所在工序，方便按产线统计。当场解决不了的可以一键转成维修工单，巡检发现写入工单说明，`patrol_records.work_order_id` 与工单历史里的 `FROM_PATROL` 事件双向留痕；转单会触发设备状态联动（设备进入"已报修"）。

## 设备状态

状态六个值：在用、闲置、停用、报废由管理员手工维护；已报修、维修中由维修工单自动维护，不接受手工写入。

状态由该设备的未结工单**推算**得出，而不是在报修和结单时命令式地设置：

- 存在处于维修中、等待零件、外协中、待试运行或待审核的工单 → 维修中；
- 否则存在处于已提交、已接单或已到场的工单 → 已报修；
- 否则回到 `baseline_status`。

`equipment.baseline_status` 存的是“没有未结工单时该设备应该是什么状态”。管理员在档案里改状态改的就是它，所以维修期间的手工修改不会被工单冲掉，而是在结单后生效。推算逻辑幂等，任何时候重算结果一致，同一台设备挂多张工单也不会算错。

报修时如果没有指定设备，或后来用“修正故障设备”改了归属，系统会对涉及的每一台设备重新推算，避免设备卡在维修态。每次状态真正发生变化都会写入审计日志，可在设备档案的“档案修改”里查到。

## 导入与结构删除

设备台账支持系统模板，也可直接读取项目中的“设备命名建议”工作表。上传只进行预览，不写入设备；只要存在待核实、类型无效、规格格式错误或重复资产编号，确认按钮就会禁用。全部通过后整批提交，任何一步失败都会全部回滚。

误建的车间、产线、工序和机位可以递归删除。删除前系统会统计整个下级分支；若存在设备安装历史或组合变动记录，必须保留结构并禁止删除。关联维修工单及其零件、流转历史会随分支一并删除，不作为阻断条件。成功删除会保留操作者、时间和分支快照的审计记录。工厂不允许通过此功能删除。
