## 2026-08-05 技改任务全面审查与缺陷修复

- 对技改任务闭环做了一轮全面代码审查（后端、前端、Android、文档四路），修复其中最影响日常使用的四个缺陷：
  - `replaceItems` 编辑草稿时交换项目顺序、或删项后复用序号/引用编号会撞 `UNIQUE(task_id, sequence_no)`/`UNIQUE(task_id, client_ref)` 直接 500。改为先把本任务全部行的两个唯一键挪进负区/置空再写回终值；被移除的行永久让出序号和引用（约束连同 `active=0` 的历史行一起生效）。
  - `addModificationItemPhotos` 未包事务：批次里任一张照片非法时，前几张已入库的附件行不回滚，文件却被清掉，留下指向不存在文件的孤儿记录，`revision_no` 也可能缺失。已整体包进 `transaction()`，历史事件同批落库。
  - 前端编辑任务时用 `toISOString()` 回填 `datetime-local`，东八区下计划时间显示早 8 小时，每编辑保存一轮就静默前移 8 小时。改为按本地时区换算。
  - `labels` 对象重复键：技改的 `CREATE/UPDATE`（新增/资料调整）被设备履历的旧键（建档/修改档案）覆盖。拆出独立的 `modificationActionLabels`，两套语义不再共用一个字典。
- Android：恢复维修通知的重启兜底清扫——上一轮把 `getActiveNotifications()` 扫描搬进任务通知后只清 `id >= TASK_NOTIFICATION_BASE` 区间，服务进程被杀重启后，重启前挂出、期间已被他人接单的维修通知会一直留在通知栏。现在 `showRepairs` 按 `[REPAIR_NOTIFICATION_BASE, TASK_NOTIFICATION_BASE)` 区间同样兜底清扫。此改动只恢复既有行为，仍需按 §6.10 在真机上验证通知流程后再交付 APK。
- 新增两个回归测试：草稿交换顺序/复用被删项序号与引用、照片批次部分失败整批回滚。全量 158 项：157 通过、1 跳过、0 失败。
- 审查发现但本轮未修（按影响排序，留待决策）：审核无「提交人不能自审」限制（旧流程有）；`reviseModificationTask` 先落状态后跑事务，失败请求会把任务从待审核拖进修订中；发布校验与审批校验不对齐（如 INSTALL 不预检设备是否已安装，可能施工完审批必失败）；存量 PENDING 旧版变动申请在 410 后无出路；创建任务未走幂等；Bearer 令牌读得到通知但 `/read` 不在白名单；文档上传限额有并发窗口；施工期可删除已发布方案引用的图纸；`prepareInstall` 不重置编辑态。
- 同步修正 DEVGUIDE/README 与代码不符处：行数/路由数/方法数/视图数/dashboard 统计数等计量全部更新；补齐漏列的 6 个测试文件和脚本清单；`WAITING_PARTS/OUTSOURCED` 实际可回 `ARRIVED`；附件类型补 `MODIFICATION_ITEM`/`MODIFICATION_DOCUMENT`；改密闸门白名单补全；删除对不存在的 browser-layout/fault/picker.js 的引用；README 三处旧名「设备变动」改为「技改任务」，并移除「提交人不能自审」这条已不成立的声明。

## 2026-07-26 修普工页布局塌陷（用户截图发现）

### 症状
普工登录进去，整页内容被压成左边一条约 190px 宽的竖带，右边一大片空白；"设备报修"四个字折成两行，eyebrow 文案两三个字就换行，表单字段和工单列表全被切掉。

### 原因
`applyLevelUi()` 给普工把侧栏 `hidden = true`，但 `.shell` 是 `grid-template-columns: 190px 1fr`——**隐藏一个网格子项并不会让网格少一列**。侧栏 `display:none` 之后，`main` 顶到了第一列（190px）里，右边那个 `1fr` 列空着。`main { overflow: hidden }` 又把溢出内容裁掉，所以看起来像是"内容被压扁"。

实测量到的对照很直接：

| | shell 列 | main 宽 | main 左边距 | 标题高 |
|---|---|---|---|---|
| 管理员（侧栏可见） | `190px 1410px` | 1410 | 190 | 37 |
| 普工（修复前） | `190px 1395px` | **190** | **0** | **74**（折行） |
| 普工（修复后） | `1585px` | 1585 | 0 | 37 |

### 这个 bug 存在多久了
`document.querySelector('.sidebar').hidden = current <= LEVELS.WORKER;` 这一行在**初始化提交里就有**（`git log -L` 查过）。也就是说**普工页从第一轮起就一直是坏的，前面四轮实测全都没发现**。

原因很明确：前几轮的浏览器实测只断言 DOM **取值**——选中项对不对、文案对不对、角标在不在——**从来没有量过任何一个元素的宽度**。异常列表干干净净，功能断言全绿，界面却是塌的。这是我的验证方法本身的漏洞，不是运气问题。

### 本次改动
- CSS 加 `.shell.no-sidebar { grid-template-columns: 1fr; }`，`applyLevelUi()` 里跟着 `classList.toggle`。没用 `:has()`——显式类不依赖浏览器特性。
- 顺手修了**同一类的第二个坑**：`hidden` 属性只是 UA 样式表的 `display: none`，优先级最低，`.form-card label { display: grid }` 一出手就把它盖掉了——上一轮新加的 `#repair-process-label`（"选了已登记位置的设备就隐藏工序栏"）**根本没生效过**。代码里原先有四处针对单个选择器的 `[hidden]` 补丁，说明这坑反复踩；已换成一条全局兜底 `[hidden] { display: none !important; }` 并删掉那四处。
- 新增实测脚本 `browser-layout.js`：量几何而不是取值。管理员页作对照，检查横向溢出、main 占比、表单宽度、标题折行、`hidden` 是否真的生效，并在 1600/900/480/380 四个宽度下各跑一遍。
- DEVGUIDE 新增 §6.1b 和 §6.1c 两条坑，§6.7 补上"异常为空不等于界面是对的，改布局必须量几何"，以及几条实测脚本自己踩过的毛病（`Network.enable` 顺序、临时库要先删、`pkill -f` 会杀到自己的 shell）。

### 已知且刻意保留
`body { min-width: 1080px }`，所以窗口宽度在 760~1080px 之间会有横向滚动条（实测 900px 时 `scrollWidth` 1080）。桌面优先是既有决定，各角色各页面一致，响应式归到手机化路线图。760px 以下走移动断点，实测无溢出。

### 验证
单元测试 113 项全绿；**五套浏览器实测全过**（新增的 layout 一套 + 原有四套），运行期异常均为空；截图目视确认普工页恢复正常。

## 2026-07-26 普工报修减负：故障分类后移 + 补齐四段时长

### 为什么

前提是查过的：线上库 `work_orders` **0 条**（205 台设备、1 个管理员账号），报修模块还没投产。所以放宽报修必填项不会让任何历史工单变成脏数据。

### 本次改动

**故障码：不是删掉，是把录入点从报修挪到结单。**
上一轮特意堵死了"只填自由文本"的旁路，这次**不是重新打开它**——旁路的危害是故障统计落空，而这里只是换人填：到场看过的技术员分类本来就比普工准。
- `createWorkOrder`：`fault_code_id` 改选填；不选就**必须写一句话**（否则这张工单对技术员没有任何信息量），那句话回填成故障现象。
- `transitionWorkOrder` 新增第三道结单硬校验：`fault_code_id` 为空拒绝结单。三道硬校验（试运行结果 / 故障设备 / 故障代码）**都对取消和撤回豁免**。
- 新增 `classifyWorkOrder()` + `POST /api/work-orders/:id/fault-code`。补码后 `fault_symptom` 被重写成三级文本，**普工原话仍在 `description` 里不会丢**。

**工序不用选了。** 设备装在哪个机位、机位属于哪道工序，`equipment_installations` 里就有。把 `createPatrolRecord` 里已有的推导抽成 `processIdForEquipment()` 两处共用。推不出来（设备没登记安装位置）或选了"无法判断具体设备"时，工序才显示并变必填。

**常见故障快捷按钮**（`frequentFaultCodes()`）：按该设备类型的历史频次排。但库里 0 条工单，头几周频次表是空的——**冷启动会是一排空按钮**。所以加了 `fault_codes.is_common` 作为回退依据。
> 一开始想用"综合类优先"这种启发式，但类别名管理员随时能改，magic string 会静默失效。改成显式标记：预置数据里标好（整机不启动/无法正常工作/温度过高/漏油/漏料——都是站在机器边上就判断得了的），管理员也能自己调。加列时补一次，且**任意一条已为 1 就不再补**，否则管理员取消掉的标记会在重启后复活。

**四段时长**：加 `assigned_at` / `arrived_at` 两列，技术员操作一步没变。`assigned_at` 用 `COALESCE` 保护，转派不覆盖首次接单时刻。总览页加近 30 天平均响应/平均维修，**只统计时间戳齐全的工单**（老工单为 NULL，算进去会拖低均值），没数据时返回 `null` 而不是 `0`——`0` 会被读成"响应零延迟"。

### 实测挡下来的一个设计错误
第一版把说明栏写成**无条件必填**。结果：普工点了快捷按钮（等于选完三级分类）**还得再打一段字**——本轮减负的核心收益直接被自己抹掉了，而且和服务端规则不一致（服务端只在没选码时要求）。

是**上一轮留下的实测脚本 `browser-fault.js` 把它挡下来的**：那个脚本走的是"选完三级分类后提交"，说明栏必填让它静默卡在 HTML5 校验上，一张工单都没建出来。改成"选了码就变选填"。

- 快捷按钮里 `漏油`/`漏料` 带 `requires_photo`，点完提交才被拦。已在按钮上先标「· 需拍照」。

## 2026-07-26 工单评价 + 结单权限下放技术员 + 撤回与重新报修

### 为什么
**这一条推翻了第一轮的决策。** 第一轮定的是"技术员抢单、修到待审核为止，管理员验收结单"。实际跑下来两个问题：管理员不在线时工单卡住；而且真正知道"修没修好"的是报修的那个人，不是管理层。

这轮把闭环换成**服务评价模式**：技术员自己结单，报修人打分。管理层的验收由服务对象的评价替代。同时补两个防错口子——错报能撤回、没修好能重新报修。

### 关键决策
| 决策点 | 选定 |
|---|---|
| 技术员可见性 | 只能看自己的**综合平均分**，看不到单条评价、看不到谁评的 |
| 结单流程 | 取消「待审核」，技术员试运行完直接结单 |
| 评价维度 | 维修质量 + 服务态度 + 响应速度，三项五星 + 选填文字 |
| 撤回边界 | 技术员**到场前**都能撤，必须填原因 |

用户原本说"评价只有一级工人和管理员能看到"。我提出完全屏蔽的副作用——技术员不知道自己分低就无从改进，管理员拿评分找他谈话时他会觉得是黑箱——用户改选了"只看自己的综合平均分"，既有反馈又没法反推是谁给的低分。

**「待评价」不是新状态**，是 `LEFT JOIN` 算出来的 `has_review`。工单终态仍只有 `COMPLETED`/`CANCELLED`，评价没交不会让工单卡住。

### 本次改动
- `domain.js`：`TRIAL_RUN` 加 `COMPLETED`；`PENDING_REVIEW` **保留**且仍可达 `COMPLETED`——改造前可能有工单停在那，删掉就永远结不了单。新增 `WITHDRAWABLE_STATUSES`、`REVIEW_DIMENSIONS`、`assertReviewScore`。
- `db.js`：新增 `work_order_reviews`（一单一评，存技术员姓名快照供离职后统计），`work_orders` 加 `reopened_from_work_order_id`。
- `service.js`：结单权限改为 `[TECHNICIAN, ADMIN]`、取消仍 `[ADMIN]`；新增 `withdrawWorkOrder`（按"是不是本人"判权限，不按级别）、`reviewWorkOrder`、`myReviewSummary`、`listReviews`、`technicianRanking`、`reopenWorkOrder`。
- `server.js`：6 条新路由；**`/api/meta` 开始下发状态机**（见下）。
- 前端：星级控件（三维度、手机上够大）、评价/撤回/重新报修三个抽屉、普工工单卡片按状态给动作、技术员总览页的「我的服务评价」卡、管理员的「服务评价」页。

### 两个在浏览器实测里才暴露的问题
1. **前端有一份状态机的手抄副本**（`nextStatuses`），改了后端没改它，界面上给出了后端会拒绝的"待审核"选项。改成由 `/api/meta` 下发，前端不再抄第二份。同一处还有第二层旧规则：`renderWorkOrderDetail` 把 `COMPLETED` 从技术员的可选项里过滤掉了。
2. **评价内容从工单历史漏给了技术员** ⚠️ 接口层已经把 `review` 剥成 `null`，但我把评论写进了 `history` 的 `note`、分数写进了 `details_json`——而工单历史对技术员是可见的。改成只记一句"报修人已提交评价"，并补了一条专门的回归测试（把整个返回体 `JSON.stringify` 后断言不含评论原文）。**接口层过滤不等于数据不外泄，得把所有返回通道都过一遍。**

## 2026-07-26 报修做深：故障代码三级分类 + 现场照片 + 巡检

### 为什么
对照仓库里两份旧系统 YEMS 用户指南（`20260722122805.pdf` 小程序端、`20260722122742.pdf` 后台端）与需求说明书后发现：**需求书 24.1「一期必须实现」的 20 项里，没做的 5 项全部集中在操作端**——点检模板和任务、点检异常转维修、保养计划和任务、故障三级分类、报修图片。

旧系统普工报修是「扫码 → 选故障代码 → 描述 + 拍照」，新系统这两步都没有：故障现象只是一个自由文本框，照片完全没有。结果是**每张工单都无法进统计**（算不出"哪类故障最多、哪台设备最爱坏"），技术员到场前也看不到现场情况。

### 关键决策
- **故障代码不替换 `fault_symptom`，而是回填它**。该列是 `NOT NULL` 且工单列表、设备履历、审计到处在显示。新增 `fault_code_id` 外键，服务端把所选故障码的可读文本（"机械故障 / 轴承 / 异响"）回填进 `fault_symptom`——下游展示一行没改，同时拿到了可统计的结构化字段。
- **不留兼容旁路**。第一版实现里留了"只传 `fault_symptom` 也能建单"的兼容路径，跑测试时发现**现有 41 个测试一个没红**——说明这条旁路让"故障代码必选"形同虚设。当场删掉，改成硬性必选，然后把 ~20 处测试调用点全部补上 `fault_code_id`。
- **照片走现成的 base64 通道**，不引入 multipart 依赖（DEVGUIDE §一 第 1 条铁律）。前端 canvas 压到长边 1600px / JPEG 0.8 再传。
- **服务端只认魔数字节**，不信前端声明的 mime——否则改个扩展名就能往服务器上传任意文件。
- **巡检按用户的定义做，不是旧系统那种逐项打勾的巡检表**：技术员每天到现场转，扫码选设备 → 拍照 → 一个必填文本框写"发现了什么、怎么处理的"。刻意做得轻，否则没人愿意每天填。

### 本次改动
- 新增 `src/fault-codes.js`：把旧系统截图里那 21 个扁平故障码整理成 23 条三级建议值（电气/机械/液压气动/综合）。漏油、外观损坏这类 `requires_photo=1`，"异响"这种拍了没用的不强制。全部 `is_seeded=1`，**只在表为空时种入**——管理员删掉的预置项不会在重启后复活（有真实文件库的重启测试兜着）。
- `db.js`：新增 `fault_codes` / `attachments` / `patrol_records` 三张表，`work_orders` 加 `fault_code_id`，`app_meta` 加 `patrol_sequence`。
- `service.js`：故障码 CRUD（已被工单引用的只能停用）；`storeAttachment(s)` 落盘+写库+失败清理；`resolveReportedFault()` 处理必选、兜底码强制补充说明、默认紧急程度与停机标记；`createWorkOrder` 改为整体事务（用 `nextSequenceInsideTransaction`，避免事务嵌套）；巡检增删查与 `convertPatrolToWorkOrder`；`equipmentHistory` 加照片和巡检。
- `server.js`：11 条新路由。`GET /api/attachments/:id/file` 流式返回图片并按所属工单判可见性。
- 前端：报修表单的自由文本换成三级级联下拉 + 处理建议提示 + 必须拍照时禁用提交；可复用的照片控件（压缩/预览/删除/灯箱）；新增巡检页和故障代码管理页；技术员扫码出现「登记巡检 / 报修」二选一；设备档案加「巡检记录」标签页，维修记录里显示照片；移动端断点把输入控件放大到 16px 字号（iOS 上小于 16px 会自动缩放页面）。

### 验证

- 安全相关的重点覆盖：伪装成 jpg 的文本被拒、超大/超数量被拒、**某一张失败时同批已写下的文件被清理干净且工单不会建出来**（真的去临时目录里遍历确认没有孤儿文件）、普工看不到别人工单的照片、删照片同时删磁盘文件。

## 2026-07-26 设备履历 + 报修状态自动联动

### 关键决策
- **状态用派生不用命令式**。没有写成"报修时设成维修中、结单时改回去"——一台设备同时挂两张工单时那种写法必然出错。改成可重算的 `syncEquipmentStatus(equipmentId)`：查未结工单，有开工的→`REPAIRING`，还有未结的→`REPORTED`，都结了→`baseline_status`。幂等、随时可重算。
- **新增 `equipment.baseline_status`** 存"没有未结工单时该设备应该是什么状态"。管理员在档案里改状态改的是它，所以维修期间手工改成"闲置"不会被工单冲掉，结单后自然落到闲置。
- 触发时机按用户选定：**全部报修都触发，且分两段**——提交即"已报修"，技术员开工才"维修中"。这样产线树上能立刻看出"报了但还没人接"。

- `service.js`：新增 `syncEquipmentStatus()`；在 `createWorkOrder`、`transitionWorkOrder`、`correctWorkOrderEquipment`（**新旧两台设备都调**）、`updateEquipment` 四处接线。`updateEquipment` 原来 `String(input.status || current.status)` 在设备处于 REPAIRING 时会抛"设备状态无效"，改成写 `baseline_status` 再重算。`dashboard()` 加 `repairingEquipment` 计数。

## 2026-07-26 修复登录后白屏：`event.currentTarget` 在 await 之后是 null

### 为什么
用户报"设置密码了但登不进去，Cannot read properties of null (reading 'reset')"。

### 根因
async 事件处理函数遇到第一个 `await` 就返回，事件派发随即结束，`event.currentTarget` 被置为 `null`：

```js
await api('/api/session', ...);   // 密码校验通过、Cookie 已下发
event.currentTarget.reset();      // ← null.reset()，抛错
await startSession();             // ← 永远走不到，所以"登不进去"
```

### 本次改动
- `login-form` 和 `first-password-form` 两处（本次引入的）改为先同步存 `const form = event.currentTarget`。
- 顺手修了**原有代码里同样的两处**：设备台账新建表单、设备变动提交表单——它们提交成功后表单不清空并静默抛错，一直没人发现。
- `serveStatic` 加 `Cache-Control: no-cache`，免得改了前端浏览器还在跑旧脚本。
- DEVGUIDE §6.1 把这条记为一级坑。

### 验证
- 确认剩余 16 处 `event.currentTarget` 全部在 await 之前同步求值（作为参数传入是安全的）。
- **这次改用无头 Chrome 真跑界面**，不再只验接口：登录页正常挡在最前 → 错误密码提示"工号或密码不正确" → 正确密码跳强制改密 → 改密后进入系统 → 普工只有一个页面、提交报修后出现在"我的报修" → 技术员看到"待接单"分组和"我接这单" → 技术员的台账/产线树写入按钮全部不渲染 → 技术员工单详情里没有"已完成"选项 → 管理员能指派。`Runtime.exceptionThrown` 全程为空。

### 教训
上一轮只做了接口层验证就说"前端没问题"，这是不够的——这个 bug 接口全绿但界面完全不可用。涉及界面的改动必须用真实浏览器跑一遍并监听运行期异常。

## 2026-07-26 三级成员管理 + 普工报修

### 为什么
用户要"普工报修、技术员维修"，并要三级成员管理。摸清现状后发现两个前提事实决定了这次改动的形状：
1. **报修后端已经完整存在，只是被开关关掉了**：工单状态机、零件记录、历史时间线全都写好并有测试，`server.js` 用 `YSM_REPAIR_MODULE_ENABLED` 把 `/api/work-orders/*` 拦成 503，前端报修页被 `hidden` 藏起。所以是"开启 + 补权限 + 补普工界面"，不是从零开发。
2. **系统没有"成员"概念，权限是假的**：角色是页面右上角一个下拉框，经 `X-Role` 请求头传给后端，任何人可自选"系统管理员"。`流程优化评估报告.md` 早就指出审计日志的操作人因此不可信。要做三级管理必须先补真实的用户表、密码登录和会话，否则三级形同虚设。

### 关键决策（用户拍板）
| 决策点 | 选定 |
|---|---|
| 派单/结单 | 技术员自己抢单，管理员验收结单 |
| 登录 | 全员账号+密码，管理员开户，首次强制改密 |
| 旧角色 | 生产主管、设备科合并进管理员，严格三级 |
| 普工可见性 | 只看自己报修的工单 |

**三级映射是本次最省事的设计**：`ROLES` 五个常量继续作为内部权限令牌，用户表只存 1/2/3，登录时映射为 `EMPLOYEE`/`TECHNICIAN`/`ADMIN`。因为 `ADMIN` 本来就在每一处 `assertRole` 的允许列表里，几十处权限校验**一行没改**；而结单要求 `[PRODUCTION_SUPERVISOR, ADMIN]`，技术员天然被挡在外面，正好就是要的流程。

### 本次改动
- 新增 `src/auth.js`：`node:crypto` 的 scrypt 加盐哈希（`timingSafeEqual` 比较）、会话签发/解析/滑动续期/失效、级别↔角色映射、Cookie 解析。**不引入新依赖**。
- `db.js`：新增 `users` / `sessions` 两张表，`work_orders` 加 `reporter_user_id` / `assignee_user_id`，新增 `seedAdmin()`（没有任何 level=3 用户时建 `admin` / `ysm-admin-2026`，`must_change_password=1`）。
- `service.js`：成员管理一组方法（列表/开户/改级别停用/重置密码/改自己密码/登录）。开户和重置生成一次性密码**只在响应里返回那一次**；任何返回值都不含 `password_hash`/`password_salt`；登录时用户不存在也做一次哈希运算，避免用响应时间区分"账号不存在"和"密码错误"；系统始终保留至少一个启用的管理员；改级别或停用立即踢掉旧会话。
- `service.js` 工单侧：`listWorkOrders(context)` 对普工加 `reporter_user_id` 过滤；`getWorkOrder(id, context)` 普工看他人工单抛 403（`context` 默认 `null` 表示服务内部调用不过滤）；`assignWorkOrder` 允许技术员**自己抢单**（只能指派给自己、抢不走别人已接的单），管理员可强制转派。
- `server.js`：**彻底删除 `X-Actor`/`X-Role` 请求头的信任路径**，改为只从 `ysm_session` HttpOnly Cookie 解析；公开白名单只留 `GET /api/health` 和 `POST /api/session`，其余无会话一律 401；未改密时除改密/登出外全部 403；新增会话与成员共 8 个端点；删除 `YSM_REPAIR_MODULE_ENABLED` 开关和那段 503 拦截。
- 前端：登录闸门 + 强制改密表单；顶栏的操作人输入框和角色下拉**整个删掉**，换成姓名/级别 + 改密 + 退出；`applyLevelUi()` 按 `data-min-level` 隐藏入口；普工只有一个报修页（侧栏整个隐藏）；技术员看到"待接单/处理中/已结束"三组工单和"我接这单"按钮；新增成员管理页；扫码后直接落到报修页并预填工序和设备。
- `scripts/http-smoke.js` 改为先登录再冒烟，并断言未登录时业务接口返回 401。
