# 手机化路线图

> 目标：让普工在车间用手机**扫设备铭牌 → 拍张照 → 提交报修**，技术员在手机上接单和填维修记录。
> 本文按阶段拆分，每阶段都能独立交付、独立验收，**不做完下一阶段也能用**。
> 结论先行：**阶段 0 是硬前置，不做它后面全部无意义**；做到阶段 2（PWA）绝大多数工厂场景就够了，阶段 4（打包 APK）是可选项而不是必经之路。

---

## 一、先认清现状：现在手机上打不开

不是界面问题，是三个硬约束。**这三条不解决，做再多界面优化手机上也看不到。**

| # | 约束 | 现状 | 后果 |
|---|---|---|---|
| 1 | 服务只监听本机 | `src/server.js:30` `HOST` 默认 `127.0.0.1` | 手机和服务器在同一个 WiFi 里也连不上 |
| 2 | 二维码里存的是本机地址 | `PUBLIC_BASE_URL` 默认 `http://127.0.0.1:8787` | 铭牌打出来手机扫了打不开 |
| 3 | 相机 API 需要安全上下文 | 现在是纯 HTTP | 浏览器只在 HTTPS 或 localhost 下允许 `getUserMedia`，**页面里没法直接调摄像头扫码** |

好消息是**代码侧几乎没有历史包袱**：

- 前端零框架、零构建，只用了 `FileReader` / `localStorage` / `navigator.clipboard` / `window.print` 四个浏览器 API，全部在手机浏览器和 WebView 里可用；
- 身份是 HttpOnly Cookie + 同源请求，天然适配 PWA，也能在 WebView 里工作；
- `styles.css` 已经有一个 760px 断点，把栅格降成单列、侧栏改成横向滚动，**基本框架在了，只是没针对车间场景打磨**；
- 扫码链路已经通了：铭牌二维码 → `/?scan=<token>` → `handleScanLink()` 解析 → 落到报修页并预填工序和设备。缺的只是"地址得是手机能访问的"。

## 二、三条技术路线怎么选

| 方案 | 用户怎么装 | 能用相机/推送吗 | 工作量 | 适合什么时候 |
|---|---|---|---|---|
| **响应式 Web**（阶段 0-1） | 浏览器输网址／扫码打开 | 拍照可以（`<input type=file capture>`）；站内扫码要 HTTPS | 小 | 立刻能上，先跑起来 |
| **PWA**（阶段 2-3） | 浏览器"添加到主屏幕"，图标和 App 一样 | 相机、离线缓存、Android 上可推送 | 中 | **推荐终点**，绝大多数工厂够用 |
| **Capacitor 打包 APK**（阶段 4-5） | 装 apk 包（不必上应用商店） | 全部原生能力 + 稳定推送 | 大 | 确实需要推送叫醒、或 IT 要求统一装包时 |

**建议**：直奔 PWA。它不需要应用商店审核、不需要用户更新（改完刷新即最新）、开发链路仍然是现在这套零构建的 HTML/JS。等到"技术员必须被推送叫醒"成为刚需时，再用 Capacitor 把同一套页面包成 APK——**那时页面代码不用重写**，这也是为什么前面几个阶段的投入不会白费。

## 三、分阶段计划表

工时是**粗估**，按一个人专注开发算，不含现场调试和沟通。

### 阶段 0 · 让手机能连上（硬前置）

| 项 | 内容 |
|---|---|
| **目标** | 手机在车间 WiFi 下能打开系统并登录，扫铭牌能跳到报修页 |
| **前置** | 需要 IT 给一个**固定内网 IP 或内网域名**；服务器（现在是这台 Linux 机器）常开 |
| **工作量** | 1–2 人天（多数时间在网络和证书，不在代码） |

做什么：

1. `HOST=0.0.0.0` 让服务对局域网可见；服务器设固定 IP（或内网 DNS 一个名字，如 `sb.ysm.local`）。
2. **配 HTTPS**。三个选择：
   - 内网域名 + 公司内部 CA 签发证书（最正规，需要 IT 在手机上装根证书）；
   - 有公网域名的话用 Let's Encrypt DNS-01 签发（不需要服务器暴露公网）；
   - 自签证书（最快，但手机每次都提示不安全，且**部分浏览器仍会拒绝给相机权限**，只适合临时验证）。
   前面加一层 Nginx/Caddy 做反代，Caddy 配置最省事。
3. 设 `YSM_SECURE_COOKIE=1`（会话 Cookie 加 `Secure`）。
4. **`PUBLIC_BASE_URL` 改成最终地址**，然后才批量打印铭牌。
5. 服务器防火墙只放行内网段。

**验收**：手机连车间 WiFi → 浏览器打开 `https://<地址>` → 登录成功 → 用手机自带相机扫一张测试铭牌 → 直接跳到报修页且工序设备已预填。

> ⚠️ **地址一旦定下来就别改**。铭牌贴到设备上很难换；`qr_mappings` 里的 token 是稳定的，换地址只需改环境变量重新打印，但**已经贴出去的旧牌会全部失效**。这就是 README 里"正式地址定下来前只打印少量测试铭牌"的真正原因。

### 阶段 1 · 移动端体验打磨 + 拍照报修

| 项 | 内容 |
|---|---|
| **目标** | 普工单手在手机上 30 秒完成一次带照片的报修 |
| **前置** | 阶段 0 |
| **工作量** | 3–5 人天（其中附件功能约占 2–3 天） |

做什么：

1. **报修表单重做移动优先**：单列、输入框和按钮高度 ≥44px、提交按钮吸底、故障现象改成常用短语快选 + 自由输入（车间打字慢）、紧急程度和"是否停机"改成大号分段按钮。
2. **拍照上传**（这是普工最需要、目前完全没有的功能）：
   - 前端 `<input type="file" accept="image/*" capture="environment">` 直接调后置摄像头；
   - 提交前在 canvas 里压到长边 1600px、JPEG 质量 0.8，避免几 MB 原图把车间 WiFi 拖垮；
   - 后端新增 `attachments` 表（`work_order_id` / `file_path` / `mime` / `size` / `uploaded_by` / `created_at`）和 `POST /api/work-orders/:id/attachments`，文件落 `data/attachments/`，**沿用现有的 12MB 请求体上限和 base64 传输方式**（和 Excel 导入一致，不引入新的 multipart 依赖）；
   - 工单详情和设备履历的维修记录里展示缩略图。
3. **技术员的移动端维修记录**：诊断/维修方法/零件三个表单在手机上是分开保存的，合成一个可折叠的长表单一次提交（`流程优化评估报告.md` 里提到的"处理一张工单要保存多次"）。
4. **登录页移动优化** + 记住工号。

**验收**：找一个真的普工，不培训，让他扫码报修一次并带照片。**看他卡在哪一步**——这一步比任何自测都有价值。

### 阶段 2 · PWA：装到主屏 + 站内扫码

| 项 | 内容 |
|---|---|
| **目标** | 手机主屏上有个"设备报修"图标，点开就是全屏 App；在 App 里直接扫码，不用切到相机 |
| **前置** | 阶段 0（HTTPS 是 PWA 和相机的硬要求） |
| **工作量** | 3–4 人天 |

做什么：

1. **`web/manifest.json`**：`name` / `short_name`（"设备报修"）/ `start_url: "/"` / `display: "standalone"` / `theme_color: "#13251c"`（用现有顶栏色）/ 192 和 512 两个图标；`index.html` 加 `<link rel="manifest">` 和 iOS 的 `apple-touch-icon`。
2. **Service Worker**（`web/sw.js`）：只做**应用壳缓存**（`index.html` / `app.js` / `styles.css` / 图标），API 请求一律走网络不缓存——设备状态和工单必须是实时的，缓存了反而害人。加版本号，发版时改版本触发更新。
3. **站内扫码**：
   - Android Chrome 用原生 `BarcodeDetector`（零依赖，识别快）；
   - **iOS Safari 不支持 `BarcodeDetector`**，需要 fallback。要么保留"用系统相机扫"的引导，要么引入一个纯前端解码库（会打破"零依赖"原则，需权衡）；
   - 扫到后走现有的 `handleScanLink()` 逻辑，不用重写。
4. 顶部加"添加到主屏幕"引导（首次访问且未安装时）。

**验收**：Android 手机添加到主屏 → 从图标启动是全屏无地址栏 → 点"扫码报修"直接出取景框 → 扫铭牌 → 表单已预填。iOS 上至少能装到主屏并正常使用（扫码可退化为系统相机）。

### 阶段 3 · 弱网与离线报修（可选，看车间网络）

| 项 | 内容 |
|---|---|
| **目标** | 车间信号差的角落也能报修，联网后自动补交 |
| **前置** | 阶段 2 |
| **工作量** | 3–4 人天 |
| **要不要做** | **先测网络再决定**。车间 WiFi 覆盖良好就跳过——离线同步的复杂度和它防的问题要匹配 |

做什么：

1. 报修提交失败时存 IndexedDB 待发队列，Service Worker 的 `sync` 事件或前台重连时补发。
2. **必须带幂等键**：前端生成 `client_request_id`（UUID）随报修一起提交，后端加唯一约束，重复提交返回原工单而不是建第二张。**没有这一步，弱网重试会造成一堆重复工单，比不做离线更糟。**
3. 照片同样进待发队列（注意手机存储配额）。
4. 界面上明确显示"待发送 N 条"，别让人以为已经报上去了。

**验收**：飞行模式下提交两条报修 → 显示待发送 2 条 → 开网 → 自动补交且系统里只多两张工单（不重复）。

### 阶段 4 · 打包成 Android APK（Capacitor）

| 项 | 内容 |
|---|---|
| **目标** | 出一个 apk，IT 统一推给车间手机，不依赖用户会不会"添加到主屏" |
| **前置** | 阶段 2 完成且稳定运行一段时间 |
| **工作量** | 4–6 人天（首次配安卓构建环境占大头） |
| **要不要做** | 只有在"用户装不明白 PWA"或"必须有可靠推送"时才值得 |

做什么：

1. 引入 Capacitor（**这会第一次给项目带来构建链**：Node + Android SDK + Gradle）。建议单独放 `mobile/` 目录，**不污染现在零构建的 `web/`**。
2. 决定 WebView 加载哪儿：
   - **加载远程 URL**（推荐）：apk 只是个壳，页面还是服务器上那份，改完即生效不用重新发包；
   - 打包本地资源：离线可开，但每次改前端都要重新发 apk。
3. **注意 Cookie**：WebView 里 origin 处理和浏览器不同，`SameSite=Lax` 的会话 Cookie 需要实测；必要时给 App 端加一条 token 认证路径（`auth.js` 的会话层已经抽出来了，加一种凭据载体不难）。
4. 相机、存储权限走原生插件；扫码换成 Capacitor 的条码插件（比 `BarcodeDetector` 兼容性好）。
5. 签名、版本号、内部分发渠道（不必上应用商店）。

**验收**：apk 装到三台不同品牌的安卓机上，扫码、拍照、报修、接单全流程通过。

### 阶段 5 · 推送通知

| 项 | 内容 |
|---|---|
| **目标** | 有新报修时技术员手机响一下；有待验收工单时管理员收到提醒 |
| **前置** | 阶段 2（Web Push）或阶段 4（原生推送） |
| **工作量** | 4–6 人天 |

做什么：

1. 后端新增 `push_subscriptions` 表和发送逻辑；在 `createWorkOrder`（通知全体技术员）、`assignWorkOrder`（通知被指派人）、`transitionWorkOrder` 进入 `PENDING_REVIEW`（通知管理员）三个点触发。
2. 通道选择：
   - **Web Push**：Android Chrome 可用；iOS 需 16.4+ 且必须是"已添加到主屏"的 PWA；需要 VAPID 密钥；国产安卓浏览器支持参差；
   - **原生推送（走阶段 4）**：安卓国内要接厂商推送通道（小米/华为/OPPO/vivo 各一套）才能在杀后台后仍然到达，这是**真正的工作量所在**，不要低估。
3. **加免打扰**：夜班、非工作时间、已读的不再推。推送一旦扰民就会被全体关掉，然后这个功能等于没做。

**验收**：技术员手机锁屏状态下，普工提交一条停机报修，30 秒内收到通知，点通知直达该工单。

### 阶段 6 · 生产化加固（与手机化并行，越早越好）

| 项 | 内容 |
|---|---|
| **目标** | 从"一台电脑上的单机程序"变成"车间依赖的系统" |
| **工作量** | 3–5 人天 |

一旦手机能连上、多个人同时用，下面几条就从"以后再说"变成"现在就得管"：

1. **自动备份**：现在只有手工 `cp` 出来的几个 `equipment-before-*.db`。要做每日定时备份 + 保留策略 + **定期恢复演练**（没演练过的备份不算备份）。注意 WAL 模式下在线拷贝要用 SQLite 的在线备份机制，不能只拷主文件。
2. **`node:sqlite` 是实验特性**：要求 Node ≥22.5，API 可能随版本变化。单机十几个人并发用问题不大，但要固定 Node 版本并在升级前冒烟。真到几十人并发再评估换 better-sqlite3 或 PostgreSQL。
3. **服务器别用桌面机**：现在服务跑在这台 Linux 桌面上，靠 systemd 用户服务托管——**用户注销就停了**。要么改成 system 级服务并开 linger，要么挪到一台常开的机器。
4. **日志轮转**：`data/server.log` 是 `append` 写，会一直涨。
5. **补上技术债里影响数据质量的两条**（见 DEVGUIDE §6.9）：完成工单强制填故障设备归属、台账导入幂等。手机端一放开，报修量上来，这两个口子产生脏数据的速度会快很多。

## 四、汇总与建议节奏

| 阶段 | 内容 | 工作量 | 必要性 |
|---|---|---|---|
| **0** | 局域网 + HTTPS + 地址定稿 | 1–2 天 | ⭐ 硬前置，不做后面全废 |
| **1** | 移动端体验 + 拍照报修 | 3–5 天 | ⭐ 报修带照片是刚需 |
| **2** | PWA：装主屏 + 站内扫码 | 3–4 天 | ⭐ 推荐终点 |
| 3 | 离线报修 | 3–4 天 | 看车间网络，可跳过 |
| 4 | Capacitor 打包 APK | 4–6 天 | 可选 |
| 5 | 推送通知 | 4–6 天 | 有明确需求再做 |
| **6** | 生产化加固 | 3–5 天 | ⭐ 与 0–2 并行做 |

**建议节奏**：先做 **0 → 1 → 2**（约两周），同时把 **6** 里的备份和服务托管一起办了。到这里普工已经能在手机主屏上点开图标、扫码、拍照报修，技术员能在手机上接单——**这已经是完整可用的产品**。之后观察一到两个月真实使用情况，再根据"到底卡在哪"决定要不要上 3/4/5，而不是现在就把六个阶段全排满。

## 五、现在就能定下来的两件事

不需要等开发，建议尽快确认，因为它们会阻塞阶段 0：

1. **系统的正式访问地址是什么**（内网 IP 还是内网域名）——这决定了铭牌能不能开始批量打印。**在这之前不要大批量打印铭牌。**
2. **谁来提供 HTTPS 证书**（公司内部 CA / 公网域名 / 自签）——这决定了站内扫码能不能做，以及手机上会不会一直提示"不安全"。
